# Реестр циклов Elephant Pants

Каноническое текущее состояние хранится в `valerol/ep_dashboard@main` согласно `EP-DP-DR-009`.

## Слои

- `observation/cycle-types/registry.yaml` — стабильные повторяемые типы циклов.
- `observation/cycles/<cycle_instance_id>.yaml` — один фактический экземпляр цикла на файл.
- `observation/events/<YYYY>/<MM>/<observation_event_id>.yaml` — одно append-only событие на файл.
- `observation/protocol/<protocol_or_instruction_id>/<version_id>.yaml` — версии нормативных процедур.
- `observation/indexes/cycles.yaml` — производное представление для навигации; не источник истины.
- `observation/templates/` — шаблоны новых записей; не факты проекта.

## Идентичность и повторение

`cycle_class` берётся только из словаря EP-DP: `ECONOMICS`, `IMPORT`, `LOGISTIC_IMPORT`, `LOGISTIC_RUSSIA`, `SALES`, `REPAIR_PROJECT`, `GROWTH_PROJECT`.

Прикладные названия вроде «логистика партии», «отгрузка» и «приёмка» задаются полем `cycle_type_id`; они не расширяют канонический словарь классов. Новое повторение получает новый `cycle_instance_id`. Поля `series_id` и `occurrence` связывают повторения одного типа.

Вложенность задаётся только `parent_cycle_instance_id`. Обратный список дочерних циклов вычисляется в индексе, чтобы не хранить две конкурирующие связи.

## Минимальная иерархия партии

```text
IMPORT_BATCH
└── LOGISTICS_BATCH
    ├── INTERNATIONAL_DELIVERY
    └── OZON_TRANSFER
        ├── OZON_SHIPMENT
        └── OZON_ACCEPTANCE

SALES_BATCH
└── BATCH_ECONOMICS
```

## Каноническая логистическая процедура

Полная нормативная процедура создания, повторения, складской декомпозиции и закрытия логистического дерева: [`EP-DP-LOGISTICS-CYCLE-PROTOCOL / 1.0`](observation/protocol/EP-DP-LOGISTICS-CYCLE-PROTOCOL/1.0.yaml).

Кратко:

1. Для каждой новой партии или нового валидного повторения создаются новые экземпляры родителя и подциклов.
2. Все узлы логистического дерева ссылаются на один `subject_ref` партии и связываются только через `parent_cycle_instance_id`.
3. Каждый подцикл закрывается собственным append-only событием.
4. Родитель закрывается отдельным событием после закрытия всех обязательных дочерних циклов и проверки собственного результата.
5. Если все условия `ACHIEVED` однозначно следуют из уже принятых фактов, логический родитель оформляется без нового вопроса владельцу; при неоднозначности применяется `HOLD` и запрашивается решение.
6. В GitHub сохраняются факты и ссылки на свидетельства. Загрузка первичных документов не обязательна.

## Правила записи

1. Экземпляр создаётся через `O2` после классификации `O1` и решения `OWNER_LPR`.
2. Закрытый экземпляр не используется для нового повторения. Новая работа после корректного закрытия получает новый ID и ссылку на предшественника.
3. Закрытие записывается отдельным событием с результатом, сравнением с ожидаемым результатом, evidence и решением `OWNER_LPR`.
4. События не изменяются задним числом. Исправление создаёт новое событие `SUPERSEDE` или `TOMBSTONE` с причиной.
5. Evidence хранится ссылочно; приватные документы не копируются в публичный репозиторий.
