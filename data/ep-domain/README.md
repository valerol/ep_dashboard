# Реестр домена Elephant Pants

Каноническое текущее состояние хранится в `valerol/ep_dashboard@main` согласно `EP-DP-DR-009`.

## Канонические точки входа

- [`domain-physiology/CURRENT.md`](domain-physiology/CURRENT.md) — указатель на текущую доменную физиологию.
- [`domain-physiology/EP-DP-v0.2.1.md`](domain-physiology/EP-DP-v0.2.1.md) — текущий нормативный текст.
- [`repository-map.yaml`](repository-map.yaml) — машиночитаемое зеркало структуры и текущий инвентарь.
- [`observation/protocol/EP-DP-LOGISTICS-CYCLE-PROTOCOL/1.0.yaml`](observation/protocol/EP-DP-LOGISTICS-CYCLE-PROTOCOL/1.0.yaml) — активная логистическая процедура.
- [`observation/protocol/EP-DP-OZON-WEEKLY-SALES-REVIEW-PROTOCOL/1.0.yaml`](observation/protocol/EP-DP-OZON-WEEKLY-SALES-REVIEW-PROTOCOL/1.0.yaml) — активная процедура еженедельной проверки продаж Ozon.

Физиология содержит нормативную топологию репозитория; репозиторий содержит точный текущий текст физиологии. Правило синхронизации и взаимного восстановления определено `EP-DP-DR-061`.

## Слои Observation

- `observation/cycle-types/registry.yaml` — стабильные повторяемые типы циклов.
- `observation/cycles/<cycle_instance_id>.yaml` — один фактический экземпляр цикла на файл.
- `observation/events/<YYYY>/<MM>/<observation_event_id>.yaml` — одно append-only событие на файл.
- `observation/protocol/<protocol_or_instruction_id>/<version_id>.yaml` — версии нормативных процедур.
- `observation/indexes/cycles.yaml` — производное представление; не источник истины.
- `observation/templates/` — шаблоны новых записей; не факты проекта.

## Минимальная иерархия партии

```text
IMPORT_BATCH
└── LOGISTICS_BATCH
    ├── INTERNATIONAL_DELIVERY
    └── OZON_TRANSFER
        ├── OZON_SHIPMENT
        └── OZON_ACCEPTANCE

SALES_BATCH
├── OZON_WEEKLY_SALES_REVIEW × N, не реже одного раза в 7 дней, пока SALES_BATCH открыт
└── BATCH_ECONOMICS
```

## Идентичность и повторение

`cycle_class` берётся только из словаря EP-DP: `ECONOMICS`, `IMPORT`, `LOGISTIC_IMPORT`, `LOGISTIC_RUSSIA`, `SALES`, `REPAIR_PROJECT`, `GROWTH_PROJECT`.

Прикладные названия вроде «логистика партии», «отгрузка», «приёмка» и «еженедельная проверка продаж» задаются полем `cycle_type_id`; они не расширяют канонический словарь классов. Новое повторение получает новый `cycle_instance_id`. Поля `series_id` и `occurrence` связывают повторения одного типа.

Вложенность задаётся только `parent_cycle_instance_id`. Обратный список дочерних циклов вычисляется в индексе, чтобы не хранить две конкурирующие связи.

## Каноническая логистическая процедура

Полная процедура создания, повторения, складской декомпозиции и закрытия логистического дерева находится в `EP-DP §6.9` и в отдельной версии `EP-DP-LOGISTICS-CYCLE-PROTOCOL / 1.0`.

1. Для каждой новой партии или нового валидного повторения создаются новые экземпляры родителя и подциклов.
2. Все узлы логистического дерева ссылаются на один `subject_ref` партии.
3. Каждый подцикл закрывается собственным append-only событием.
4. Родитель закрывается отдельным событием после обязательных дочерних циклов и проверки собственного результата.
5. Если `ACHIEVED` однозначно следует из принятых фактов, логический родитель оформляется без нового вопроса владельцу; при неоднозначности применяется `HOLD`.
6. В GitHub сохраняются факты и ссылки; загрузка первичных документов не обязательна.

## Еженедельная проверка продаж Ozon

Пока `SALES_BATCH` открыт, не реже одного раза в 7 дней создаётся новый `OZON_WEEKLY_SALES_REVIEW` согласно `EP-DP-OZON-WEEKLY-SALES-REVIEW-PROTOCOL / 1.0`.

1. В Ozon открывается `Цены и акции → Цены → Аналитика по продажам` за неделю.
2. Статистика фиксируется скриншотом.
3. Codex преобразует скриншот в CSV с колонками `sku`, `заказано на сумму`, `заказано товаров`, `показы всего`, `конверсия`.
4. В GitHub записываются только извлечённые факты, качество данных и ссылки на внешние свидетельства.
5. Подцикл закрывается только после решения `NEXT_STEP_SELECTED` или `NO_ACTION`; дефект данных допускает `HOLD_FOR_DATA_REPAIR`.
6. Закрытие обзора не закрывает родительский цикл продаж и запускает отсчёт до следующей обязательной проверки.

## Правила записи

1. Экземпляр создаётся через `O2` после классификации `O1` и решения `OWNER_LPR`.
2. Закрытый экземпляр не используется для нового повторения.
3. Каждый ребёнок и каждый родитель получают собственное closure-событие.
4. При однозначных фактах логический родитель оформляется без нового вопроса; при неоднозначности применяется `HOLD`.
5. Evidence хранится ссылочно; приватные документы не копируются в публичный репозиторий.
6. События не изменяются задним числом; исправление оформляется `SUPERSEDE` или `TOMBSTONE`.
